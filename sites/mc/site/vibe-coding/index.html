Vibe Coding从想法到可解释、可验证的作品
From an idea to work you can explain and verify

Vibe Coding 是用自然语言与 AI 协作开发。你负责问题、需求、判断和验证；AI 可以帮助理解代码、提出方案和实现小改动。

Vibe coding means building software with an AI collaborator through natural language. You own the problem, requirements, decisions, and verification. AI can help explain code, suggest approaches, and make small changes.

一句话原则先预测，做小改动，再测试，用证据解释结果。
One guiding rulePredict first. Make one small change. Test it. Explain the result with evidence.

01 / Project process

看见整个项目流程See the whole project lifecycle

开始写代码前，先知道自己处在哪一步。每一步都应该留下能检查的产物。

Before coding, know which stage you are in. Leave something you can inspect at each stage.

01发现问题Identify the problem
02写清需求Write requirements
03审查与计划Review and plan
04小步实现Build in small steps
05测试与修复Test and fix
06检查改动Review changes
07保存版本Save a version
08提交与反思Submit and reflect

流程可以返回上一步

测试失败时，回到需求、方案或代码找原因。需求变了，也要先更新验收标准。不要把“AI 已写完”当作“项目已完成”。

The process can loop back

If a test fails, revisit the requirement, plan, or code. If the requirement changes, update the acceptance criteria first. “AI finished coding” does not mean the project is done.

02 / Write a request

怎样提出清楚的需求How to write a clear request

告诉 AI 要解决什么问题、什么算完成，再谈如何实现。

Tell AI what problem to solve and what counts as done before discussing implementation.

需求卡：七个要素

  1. 使用者：谁会用？
  2. 问题：现在遇到什么困难？
  3. 目标：希望出现什么结果？
  4. 现状：当前行为是什么？
  5. 范围：这次改什么，不改什么？
  6. 限制：要保留哪些功能或条件？
  7. 验收：用什么操作和结果判断完成？

Requirement card: seven parts

  1. User: Who will use it?
  2. Problem: What is difficult now?
  3. Goal: What result do you want?
  4. Current behavior: What happens today?
  5. Scope: What will change, and what stays outside this task?
  6. Constraints: What must keep working?
  7. Acceptance: What actions and results prove it is done?

贯穿示例 · Running example: 火箭游戏的低燃料提示 / A low-fuel warning

模糊：“把燃料做得更好。”

清楚：“在降落游戏中，当剩余燃料不高于初始燃料的 20% 时显示‘燃料不足’。高于 20% 时不显示；重置后恢复初始状态。保留键盘和触控操作。本次不改变燃料消耗规则。”

Vague: “Make fuel better.”

Clear: “In the landing game, show a ‘Low fuel’ warning when remaining fuel is at or below 20% of the starting amount. Hide it above 20%, and restore the initial state after reset. Keep keyboard and touch controls. Do not change fuel consumption in this task.”

03 / Review requirements

怎样审需求文档How to review a requirements document

在让 AI 改代码之前，逐项检查需求。发现空白或冲突，先澄清并改文档。

Review each requirement before asking AI to edit code. Clarify gaps or conflicts and update the document first.

具体吗？“更好”“更快”“好看”指什么？有没有明确的对象和行为？

Is it specific? What do “better,” “faster,” or “nicer” mean? Is the object and behavior clear?

范围清楚吗？写出本次要做的事，以及不在本次范围内的事。

Is the scope clear? State what this change includes and what it leaves for later.

能测试吗？每条关键要求是否有可观察的输入、操作和预期结果？

Is it testable? Does each important requirement have an observable input, action, and expected result?

考虑边界了吗？例如恰好 20%、高于 20%、重置后分别会怎样？

Are edge cases covered? What happens at exactly 20%, above 20%, and after reset?

有冲突或风险吗？会不会破坏旧功能、泄露个人信息，或依赖尚未具备的资料？

Are there conflicts or risks? Could the change break existing features, expose personal data, or depend on missing information?

待澄清 · Needs clarification

“燃料少时提醒我。”少到多少？提醒出现在哪里？何时消失？

“Warn me when fuel is low.” How low? Where does the warning appear? When does it disappear?

可验收 · Ready to test

“≤20% 显示，>20% 隐藏；重置后隐藏；键盘和触控仍可操作。”

“Show at ≤20%; hide above 20%; hide after reset; keyboard and touch still work.”

审查结果：把不明确的问题列出来，确认答案后更新需求文档，再请 AI 实现。

Review outcome: List unclear questions, confirm the answers, update the requirements document, and then ask AI to build.

04 / Work with AI

让 AI 小步实现Build with AI in small steps

先让 AI 阅读和解释，再让它提出计划；你看懂计划后，才进入修改。

Ask AI to read and explain, then propose a plan. Start editing after you understand the plan.

一次协作的顺序

  1. 请 AI 找到相关文件并解释现有行为，先不改代码。
  2. 给出已审查的需求，让 AI 说明改动位置、风险和测试方法。
  3. 只做当前这一项改动。
  4. 看改动差异，问清楚每一处改动的原因。
  5. 自己运行测试和试玩；发现问题再提出下一轮具体要求。

One collaboration cycle

  1. Ask AI to locate the relevant files and explain current behavior without editing.
  2. Share the reviewed requirement and ask for the edit location, risks, and test plan.
  3. Make only this one change.
  4. Inspect the diff and understand why each part changed.
  5. Run tests and try the app yourself. Describe any failure precisely in the next request.

可复制的提示词 · Copyable prompt

请先阅读与燃料显示有关的代码，不要修改文件。告诉我当前燃料从哪里来、如何更新、在哪里显示。然后按下面已确认的需求提出最小改动计划：剩余燃料 ≤ 初始燃料的 20% 时显示提示；高于 20% 和重置后隐藏；保留键盘与触控操作；不改变燃料消耗规则。列出将修改的文件、需要测试的边界情况。等我确认计划后再改代码。

First read the code related to fuel display. Do not edit files yet. Explain where starting fuel comes from, how remaining fuel changes, and where it appears. Then propose the smallest change for this reviewed requirement: show a warning at ≤20% of starting fuel; hide it above 20% and after reset; preserve keyboard and touch controls; do not change fuel consumption. List the files you would change and the edge cases to test. Wait for my review before editing.

05 / Test after AI builds

AI 实现后如何测试How to test after AI implements

测试是拿实际结果对照需求。AI 的“已完成”描述不能代替你的运行结果。

Testing compares actual results with requirements. An AI claim of completion cannot replace what you run and observe.

01 / 自动测试

运行项目原有测试
Run existing tests

火箭项目运行 npm test。记录命令、通过或失败、失败信息。改了规则时补充对应测试。

For the rocket project, run npm test. Record the command, pass or failure, and any error. Add a focused test when a rule changes.

02 / 手动验收

按需求逐条操作
Check acceptance cases

示例：燃料 21% 不提示；20% 提示；重置后隐藏。写下预期与实际结果。

Example: no warning at 21%; warning at 20%; hidden after reset. Write down expected and actual results.

03 / 回归检查

确认旧功能仍可用
Check existing behavior

重新操作键盘和触控，检查画面、参数与重置。只测新提示不够。

Try keyboard and touch again. Check the display, settings, and reset. Testing only the new warning is not enough.

测试失败时

保留失败证据：操作步骤、输入、预期、实际、错误信息。把这些交给 AI 分析原因；修复后重跑失败用例和相关旧用例。

When a test fails

Keep the evidence: steps, input, expected result, actual result, and error message. Ask AI to investigate. After the fix, rerun the failed case and relevant existing cases.

最小测试记录：需求编号或描述｜测试环境｜操作与输入｜预期｜实际｜通过/失败｜截图或输出（如有）。

Minimum test record: requirement ID or description | environment | action and input | expected | actual | pass/fail | screenshot or output, if useful.

06 / Version awareness

建立版本管理意识Build version control habits

你需要知道“改了什么、为什么改、哪个版本可用、出错怎样恢复”。

Know what changed, why it changed, which version works, and how to recover.

每次改动的四个动作

  1. 留起点：改动前保存一个可运行版本。
  2. 看差异：确认 AI 只改了与需求有关的内容。
  3. 记原因：用一句话记录本次改动和对应需求。
  4. 可恢复：新版本失败时能回到上一个可用版本，再分析问题。

一个版本尽量对应一个小目标。不要靠“最终版2-真的最终版”辨认作品。

Four actions for each change

  1. Keep a baseline: Save a working version before editing.
  2. Inspect the diff: Check that AI changed only what the requirement needs.
  3. Record the reason: Write one sentence linking the change to its requirement.
  4. Know how to recover: Return to the last working version if the new one fails, then investigate.

Aim for one small goal per version. Avoid filenames such as “final-2-really-final.”

如果项目使用 Git，可先查看状态和差异，测试通过后再保存提交。不要把密码或密钥放进版本库。

If your project uses Git, inspect status and changes first; commit after testing. Never add passwords or secret keys to the repository.

git status git diff git add <changed-file> git commit -m "Show low-fuel warning"

如果课堂项目暂时没有 Git，至少保留“修改前可运行版本”和简短的版本记录：日期、改动、测试结果。

If your classroom project does not use Git yet, keep a working before-change copy and a short version log: date, change, and test result.

07 / Submit and reflect

提交能解释的作品Submit work you can explain

作品、证据和你的解释应当互相对应。

Your work, evidence, and explanation should agree.

提交前检查

  • 需求和验收条件已经写清。
  • 自动测试与手动验收已有真实结果。
  • 我看过改动，并能解释关键代码。
  • 我能指出当前作品仍有哪些限制。
  • 如果作业允许使用 AI，我记录了问过什么、采用了什么、怎样验证。

Before you submit

  • The requirement and acceptance criteria are clear.
  • Automated and manual checks have real results.
  • I inspected the changes and can explain the important code.
  • I can name what the current work still cannot do.
  • If AI use is allowed for this assignment, I recorded what I asked, what I used, and how I verified it.

使用边界：遵守教师对本次作业的 AI 使用要求。不要把个人资料、密码、密钥或受保护的测验题目发给 AI；不要提交自己无法解释的代码，也不要把未运行的测试写成“已通过”。

Use boundaries: Follow your teacher’s AI rules for this assignment. Do not send personal information, passwords, secret keys, or protected assessment questions to AI. Do not submit code you cannot explain or report an unrun test as passed.
